# SR-MA Web Platform — Autonomous Block A

Local Shiny + bslib application around the unchanged, PM-authorized canonical R engine. Only **Check search strategies** is enabled. It checks structural syntax; it does not validate clinical search quality, search databases, or approve any scientific Human Gate.

## Run with an existing R installation

Run commands from the toolkit root, in a separate working copy. The root scientific `renv.lock` is preserved; platform packages go into `web/.library`.

```sh
Rscript --vanilla web/bin/setup.R
Rscript --vanilla web/bin/import.R /path/to/existing/research-project
```

Import expects a project already generated by the canonical toolkit, including its project_config.yml, declared search_terms.yml and search strategy files. Import accepts only project-relative paths. It may create empty configured directories using the canonical path builder, but never overwrites input files. It snapshots only declared config/search inputs, never .env or research datasets. Repeat import to create a new immutable version after correcting inputs.

In two separate terminals, using the same user account and repository root:

```sh
Rscript --vanilla web/bin/worker.R
Rscript --vanilla web/bin/app.R
```

Open http://127.0.0.1:3838. Select a project and saved version, click **Check search strategies**, then choose an available result and download it. The worker continues if the browser/app closes. Reopening the app loads persistent state.

`SRMA_WEB_DATA` optionally sets the same persistent data directory for all processes; the default is `tools::R_user_dir("srma-web", "data")`. `SRMA_RSCRIPT` optionally selects the Rscript executable. `SRMA_ENGINE_ROOT` optionally selects the repository root. `SRMA_WEB_PORT` defaults to 3838. No scientific API key is needed. Do not expose this development server beyond loopback: authentication is outside Block A.

The setup script restores a Web-only lock generated from the tested package versions. It was not itself clean-room restored here. A working C/C++ toolchain and system libraries may be needed when CRAN must install archived source packages. The actual isolated Linux test runtime and package versions are recorded in docs/development-runtime.json and docs/BASELINE.md. Canonical R 4.6.1 lock restoration is not claimed.

## Isolated synthetic demonstration

These fixtures contain structural placeholder terms, not real clinical searches or study data.

```sh
Rscript --vanilla web/tests/baseline.R
Rscript --vanilla web/tests/foundation.R
Rscript --vanilla web/tests/contract.R
Rscript --vanilla web/tests/run.R
python3 web/tests/vertical.py
```

`vertical.py` creates a fresh local database, starts the real Shiny app, checks HTTP and JS/CSS resources, submits a persistent job through the application service, closes the application/submitter, runs two separate workers, and downloads real engine outputs through the authorization service. It writes reproducible evidence under web/evidence. UI interaction is also covered by Shiny testServer in run.R; the process-level vertical slice uses the service boundary rather than claiming a browser-click automation.

## Operator recovery and Human Gates

The service functions `web_require_gate`, `web_decide_gate`, `web_retry`, and `web_cancel` enforce membership, version scope and state rules. They are operator APIs, not finished scientific review UI. Human decisions require an explicit actor and are audited. Local gate decisions do not approve canonical scientific gates. Gate-dependent scientific operations remain disabled.

Retries are explicit and limited to two attempts for replay-safe system/dependency failures or resolved user-action pauses. Correct invalid search/configuration inputs and import a new version. Only QUEUED requests can be cancelled. Stale RUNNING attempts become FAILED after the timeout plus 60 seconds; late publication is fenced. Private technical logs are under the operational data directory's jobs subtree.

## PostgreSQL and storage

Set `SRMA_WEB_DB=postgres` and supply local libpq settings (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, optional `PGPASSWORD` or .pgpass) before importing. Use an empty dedicated development database. The migration creates its schema once and rejects checksum drift. PostgreSQL execution was not tested in this Work environment; the permitted compatible SQLite strategy was used for executable schema/state/concurrency tests.

Object storage is a put/get/checksum port with a local immutable implementation. S3 implementation and production deployment are not included. Orphaned immutable files after interruptions are retained; no destructive cleanup runs automatically.

## Engine integrity and delivery

The engine source manifest covers 98 original files. The full-source ZIP preserves their exact bytes. A checkout that changes line endings may need a documented baseline refresh; never silently waive a source-hash mismatch. The ZIP excludes original .git and secrets, while the report records original and development commits. The separate change patch can be applied to the exact original source. No remote push or main merge was performed.
